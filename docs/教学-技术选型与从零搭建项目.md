# 教学笔记：为什么选这些技术，以及怎么从零搭一个项目

> 这份笔记解决两个问题：
> ① 你朋友写的那套技术栈**为什么是这些**——不是背结论，而是学会**自己推导**；
> ② 一个项目**从零开始到底按什么顺序做**——包括新手最容易跳过、却最致命的那一步。
>
> 用法：不要一次读完。先读第一、二课（理解"是什么"和"为什么"），再对着第三课去**打开你自己的项目**逐条核对。

---

## 第一课：一个 Web 项目其实是四样东西

不管技术名字多花哨，一个联网的应用永远是这四层。用一家餐厅来类比最容易懂：

| 层 | 餐厅里的角色 | 你项目里的东西 | 住在哪 |
|---|---|---|---|
| **前端** | 大堂：菜单、桌子、服务员 | React 写的页面（`frontend/`） | **用户的浏览器里** |
| **后端** | 后厨：按规矩做菜，外人不能进 | Python + FastAPI（`backend/`） | **你的服务器上** |
| **数据库** | 仓库：食材存放，有账本 | SQLite / PostgreSQL | 服务器上（或文件里） |
| **大模型** | 外聘的顾问厨师：你租他，按次付费 | DeepSeek API | **别人家的服务器上** |

**为什么非要分成四层？三个原因，每个都是血泪教训：**

1. **安全**：前端代码用户能直接看到（按 F12 就是源码）。所以密码校验、权限判断**必须在后端**。把判断写在前端，等于把仓库钥匙挂在大堂墙上。
2. **共享**：前端是"每人一份"的（每个用户浏览器里各跑一份），但数据必须只有一份。所以数据放数据库，所有人通过后端去读写同一份。
3. **能力**：浏览器干不了重活（不能长时间计算、不能直接存大量数据、更不能藏 API 密钥）。

> **你现在就能验证**：打开 `frontend/src/api/client.ts`，看它是怎么把请求发给后端的；再打开 `backend/app/api/v1/auth.py`，看密码校验发生在哪一边。**你会发现校验全在后端。**

## 第二课：技术选型不是"选最好的"，而是"在你的约束下选最不添麻烦的"

这是整份笔记最重要的一句话。

新手以为技术选型是查排行榜；实际上它是**从约束推导**出来的。你朋友那套选型之所以"内行"，是因为每一步都能从约束推出来。

### 先明确约束（你的项目真实情况）

| 约束 | 说明 |
|---|---|
| C1 | **一个人开发**，没人接手、没人运维 |
| C2 | **没有服务器运维经验**，最好开箱即跑 |
| C3 | **要接 AI**，而且要用得起 |
| C4 | **时间有限**，要尽快出可演示的东西 |
| C5 | **国内网络环境**，国外服务可能连不上 |
| C6 | 这是**比赛项目**，要能讲清楚、能演示 |

**记住这六条。下面每个"为什么"都是从它们推出来的。**

### 2.1 为什么用 Python 写后端？

- AI 的生态几乎全在 Python（文本处理、大模型的官方 SDK 都是 Python 优先）。
- 约束 C3 直接决定了它。如果用 Java/Go 写后端，接 AI 会多绕一层。

### 2.2 为什么是 FastAPI，而不是 Django 或 Flask？

| 候选 | 它的强项 | 为什么**不**适合你 |
|---|---|---|
| **Django** | 大而全：自带后台管理、用户系统、ORM | 约束 C4：它自带的东西你大多用不上，反而要花时间学它的规矩。它偏向"整站渲染"，和你要做的前后端分离（前端 React 单独跑）不搭 |
| **Flask** | 极简，几百行就能起服务 | 它太素了：**参数校验、接口文档都要自己装自己写**。而 FastAPI 自带这两样 |
| **FastAPI** ✅ | ① 自动生成接口文档（打开 `/docs` 就能测）② 与 Pydantic 深度绑定，**数据格式校验是内建的** ③ 原生支持异步，适合"等 AI 回复"这种慢操作 | —— |

**关键理由**：约束 C1 + C4。一个人开发时，**"少写一点、少错一点"比"功能多"重要得多**。FastAPI 帮你去掉的是"手写参数校验"和"手写接口文档"这两件重复劳动——你项目里 46 条接口，如果每条都手写校验和文档，那是巨大的工作量。

> **验证**：跑起后端，打开 `http://localhost:8000/docs`。那份自动生成的接口文档**不是你写的**，是 FastAPI 从你的代码里"读"出来的。这就是它省下的时间。

### 2.3 为什么数据库一开始用 SQLite？（这条最值得学）

| 候选 | 为什么不适合你的起点 |
|---|---|
| MySQL / PostgreSQL | **要先装数据库软件、要配用户密码、要开端口**。约束 C2：你连 Python 都还没装好，先卡在数据库上，项目就死在第 0 天 |
| MongoDB | 无固定格式，但你的数据（用户、画像、任务）**关系非常明确**，用关系型数据库更合适 |
| **SQLite** ✅ | **一个文件就是一个数据库**，零安装、零配置。Python 自带驱动 |

**为什么这是对的**：SQLite 和 PostgreSQL 在你的代码里**几乎是同一套写法**（都通过 SQLAlchemy/SQLModel），所以将来要换，改一行连接配置就行。**先用能跑起来的，再用能扛量的。**

> ⚠️ 但要理解 SQLite 的两个限制（你项目里真踩过）：
> 1. **默认不强制外键**——你以为数据库会拦住的脏数据，它不拦。这就是为什么你的项目要专门加一句 `PRAGMA foreign_keys=ON`。
> 2. **并发写入弱**——同一时刻只有一个写操作。够学生项目用，但用户量上万就要换。

### 2.4 为什么前端用 React，不用 Vue？

这条**没有绝对答案**，两者都能做你的事。真实理由是：**生态和组件库**。

- React 的组件库更多（尤其"企业级/工具型"组件），遇到问题搜到的答案更多。
- 约束 C4：出问题时"能搜到答案"的速度，对一个人开发至关重要。
- **反面教材**：如果选了一个冷门框架，你会在一个没人遇到过的报错上卡三天。

**这里要学的是**：当两个选项**差不多**时，选**生态大的那个**。这不是技术判断，是风险管理。

### 2.5 为什么 UI 库从 Ant Design 换成了 shadcn/ui？

这在你项目的《勘误与决策记录》里有完整记录，是个绝好的选型案例：

- **Ant Design**：组件齐全、开箱即用，但它是**有自己审美的成品**——你想改配色、改圆角、改密度，会一直和它的默认设定打架。
- **shadcn/ui**：它**不是传统组件库，而是"把源码复制到你项目里"**。所以你能随便改。

**推导过程**：你的产品定位是"陪伴型"（像个学长），不是"中后台管理系统"。Ant Design 的气质偏后者。**当"我不满意想改"的成本很高时，选能改的那个。**

### 2.6 为什么 AI 用 DeepSeek？

| 约束 | DeepSeek | 国外模型（如 GPT） |
|---|---|---|
| C5 国内网络 | 国内直连 | 可能要代理 |
| C3 成本 | 便宜很多 | 贵 |
| 合规/国产 | 国产大模型，是加分项 | 无法作为国产替代叙事 |

### 2.7 最重要的部分：为什么"不引入"这些东西

你手册里有一节叫「明确不引入的依赖及原因」——**那一节比"选了什么"更能说明设计者是否真懂**。摘几条讲透：

| 没引入 | 表面理由 | 真正的理由（学会这个思维） |
|---|---|---|
| **Redis**（缓存/队列） | "没有刚需" | 引入任何中间件，都会带来：装它、配它、监控它、它挂了怎么办。**一个人开发时，每多一个组件就多一个半夜会崩的地方。** |
| **Celery**（分布式任务队列） | "APScheduler 够了" | 你只有一台机器。分布式队列是**为多机设计的**，单机用它等于给自行车装飞机引擎 |
| **LangChain**（AI 编排框架） | "只接一家模型" | 框架是为了**屏蔽多家模型的差异**。你只用一家，框架就只剩"多学一套抽象"的成本 |
| **向量数据库** | "不需要语义检索" | 你要的是"按用户查数据"，不是"按意思搜相似内容"。**用了不对口的工具，比不用更糟** |
| **OCR** | "用不上" | 这是**基于真实数据的判断**：为 5% 的情况做一套复杂系统，不值。另外你项目里的简历是让学生自己一个问题一个问题填出来的（`/resume`），**根本没有扫描件**，OCR 接上去也没有输入源 |

**这一课的核心**：技术选型的能力，**一半体现在"不选什么"上**。新手喜欢加东西，老手一直在减东西。

## 第三课：从零开始搭一个项目，正确顺序是什么

新手最容易犯的错是：**打开编辑器就开始写页面**。写到一半发现数据存不下、接口对不上，全部推倒重来。

正确顺序是**从里往外**，而且是**先设计、后编码**：

### 第 0 步：用一句话说清要解决什么问题

- ✅ "让不知道自己要什么的低年级学生，今天能往前迈一小步"
- ❌ "做一个 AI 就业平台"（太大，没法判断做到没有）

**为什么**：这句话是你后面所有取舍的裁判。功能要不要做？看它是否服务于这句话。

### 第 1 步：把核心闭环走一遍（用户视角）

别列功能清单，**写一个用户从进门到离开的完整故事**：

> 注册 → 做测评 → 看到画像 → 和 AI 聊天 → AI 发现我的痛点 → 给我一个任务 → 我做完打卡 → 画像变了 → 更懂我了

**为什么**：闭环之外的任何功能，都是**可选**的。你的手册里"MVP 砍掉的功能"那一节，就是拿这条线去砍的。

### 第 2 步：画数据表（**这一步是新手和熟手的分水岭**）

方法：**把故事里的"名词"圈出来**，每个名词一张表。

> 故事里有：用户、测评结果、画像、标签、对话、消息、任务、步骤、简历、面试、奖章……
> 于是有 17 张表。

每张表只回答一个问题：**"关于这个名词，我要记住哪些信息？"**

- `users`：用户名、密码哈希、学校、专业、年级
- `messages`：属于哪个对话、谁说的、说了什么、什么时候

**为什么必须先做这一步**：数据是一切的地基。**表结构错了，上面所有代码都要重写。**而表结构对了，写接口就是水到渠成。

> **验证**：打开 `backend/app/models/` 目录，每个文件就是一张表。对照你在需求文档里看到的功能，你能指出"哪个功能用到了哪几张表"吗？

### 第 3 步：列接口（后端和前端之间的合同）

把故事里的**每一个"动作"**变成一个接口：

> 注册 = `POST /auth/register`
> 看画像 = `GET /profile`
> 发消息 = `POST /chat/conversations/{id}/messages`

**为什么**：这是前后端之间**唯一的连接点**。接口定好了，前端和后端就可以**两个人并行做**（你项目里就是这么并行开发的，也因此对不上账——见第四课）。

### 第 4 步：列页面（每个页面 = 一组接口的展示）

> 登录页 = 用注册/登录接口
> 首页 = 用画像 + 任务 + 每日一问接口

**为什么放第 4 步**：**先有接口再有页面，页面就不会"想要一个不存在的数据"。**反过来做，就会不断改接口。

### 第 5 步：搭骨架，先让"啥也没有的项目"能跑起来

**这一步新手最容易跳过，但它能省掉后面 80% 的抓狂。**

具体做什么：
1. 建一个空的后端，只加一个 `/health` 接口，**确认能访问**；
2. 建一个空的前端，只有一个标题，**确认浏览器能打开**；
3. 让前端调通那个 `/health`，**看到数据从后端传到前端**。

**为什么这么重要**：这一步验证的是"**环境通了**"——Python 装对了没、端口通不通、跨域配没配、前端代理对不对。这些事和你的业务逻辑毫无关系，**但如果没通，你会误以为是自己的代码写错了**。

> 你之前 `npm run dev` 报"找不到 npm"，卡的就是这个阶段。那不是代码问题，是环境问题——**它们的排查方式完全不同**。

### 第 6 步：打通一条"最细的竖线"（**最关键的一步**）

不要按"先做完所有后端，再做所有前端"的顺序。而是：

> 挑一个最简单的功能（比如"注册登录"），把它**从数据库到接口到页面完整打通**。

一条竖线打通后，你会拥有：
- 一套**已经验证可行的**代码模板（其他功能照抄结构）
- 对全局的**真实理解**（数据怎么流、哪里容易错）
- 一个**能演示**的东西（哪怕只有 5%）

**这就是你项目里说的"M1 主闭环"**。有了这条线，剩下的功能都是"再来一条同样的线"。

### 第 7 步：横向铺功能，第 8 步：最后才美化

美化放最后，因为**好看的错误页面毫无价值**。

## 第四课：三个必须懂的概念（你项目里全都用到了）

### 4.1 前后端分离 + API 契约

前端和后端是**两个独立程序**，通过 HTTP 接口说话。它们之间的约定叫**契约**。

**你项目里真实出过的事故**（在《勘误与决策记录》第 6.2 节）：
后端严格按手册写了接口路径，前端按设计文档写了调用路径，**两边照的是不同文档**，结果前端有 **12 处调用根本不存在的地址**（比如后端是 `/resume` 单数，前端写 `/resumes` 复数）。

**教训**：接口路径、参数、返回格式，**必须有唯一权威来源**，两边都照它写。这就是为什么真实项目要维护 API 文档。

### 4.2 "统一响应格式"为什么值得较真

你项目规定：所有接口都返回 `{ code, message, data }`。

**为什么**：前端就能用**一套统一的逻辑**处理所有接口：
- `code = 0` → 成功，取 `data`
- `code ≠ 0` → 失败，弹 `message`

否则每个接口的错误处理都要单独写。**统一约定的价值，不在于它本身多正确，而在于它消除了"每次都要重新决定"的成本。**

### 4.3 状态管理：为什么前端也需要"记性"

浏览器刷新就失忆。所以需要：
- **localStorage**：跨刷新保存（比如登录令牌）——但**用户能看到**，所以不能放敏感信息；
- **内存状态（Zustand）**：页面跳转时保持（比如"我的画像"），刷新就没了。

**判断标准**：这个东西刷新后还要在吗？要 → 存 localStorage；不要 → 放内存。

## 第五课：答辩会被问什么（为什么你必须懂这些）

评委不会考你 API 细节，但一定会问**判断类问题**。这些题答不上来，会被认为"项目是别人做的"。

**Q1：为什么用这个技术栈？**
> 答法示范："因为我们是一个人开发、没有运维，所以选型原则是**依赖尽量少**。后端用 FastAPI 是因为它自带参数校验和接口文档；数据库先用 SQLite 是为了零安装就能跑，代码里通过 ORM 抽象过，将来换 PostgreSQL 只改一行配置。"

**Q2：和竞品的技术差异在哪？**
> 不要答"我们的技术更先进"，答**机制差异**：竞品是"用户提问→系统回答"，我们是"系统主动发现→给可执行路径"。

**Q3：用户数据和隐私怎么保证？**
> 你项目里**真有实现**，照着说：密码哈希存储、令牌有过期时间、越权访问统一返回"资源不存在"（"不存在"和"不属于你"用同一个错误码，防止被试探出哪些数据存在）、日志脱敏（不记密码与 API Key，越权访问不记日志以免刷日志）。

**Q4：如果用户量涨 100 倍，哪里先崩？**
> 这题考的是**你知不知道自己系统的瓶颈**。答：SQLite 的并发写入会先成为瓶颈，换 PostgreSQL 即可；其次是 AI 调用成本和响应时间，对策是上下文裁剪、轻量场景走规则不调模型。

**Q5：这个东西真的是你们自己做的吗？**
> 这题的答案不在嘴上，在**你能不能解释一个具体的 bug**。比如："我们在接入真实大模型后发现流式对话全部失败，报错是 UUID 不能被 JSON 序列化——因为那个异常发生在流已经开始之后，只能被吞成错误事件。"**能讲出一个只有做过的人才知道的坑，比任何声明都有说服力。**

## 怎么用你现有的项目来学（最有效的路径）

光看笔记记不住。建议按这个顺序**动手**：

1. **打开 `backend/app/models/user.py`** —— 这是 `users` 表。对照需求文档，说出每个字段为什么存在。
2. **打开 `backend/app/api/v1/auth.py`** —— 这是注册登录接口。对照 `/docs` 里的自动文档，看代码和文档的对应关系。
3. **打开 `frontend/src/api/client.ts`** —— 看前端怎么统一处理响应。找到 `code === 1002` 那段，想清楚"为什么这里要清 token 而不是直接跳转"。
4. **跑一遍项目**（`.\dev-backend.ps1` + `.\dev-frontend.ps1`），在浏览器里注册一个账号，按 F12 打开**网络面板**，看每一个请求发到哪、返回什么。**这一步能让你第一次"看见"前后端是怎么说话的。**
5. **故意改坏一个地方**（比如把某个接口路径改错），看报错长什么样。**学会读报错，比学会写代码更重要。**

## 最后一句

你朋友给的那套提示词是**答案**。这份笔记想做的是让你拥有**推导过程**。

有了推导过程，你就能：
- 换一个题目，**自己**选一套技术栈；
- 面对质疑时，说出**理由**而不是"别人都这么用"；
- 遇到问题时，判断"这是环境问题还是代码问题"，而不是乱试。

**这两种能力的差距，就是"会用工具"和"能做项目"的差距。**
