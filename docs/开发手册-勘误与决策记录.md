## 2. HTTP 语义

### 2.1 异常 → HTTP 状态分层 [已决策]

**唯一推导落点**是 `backend/app/core/errors.py::CODE_TO_HTTP_STATUS`：**只要业务码相同，HTTP 状态就一定相同**。

| 业务码 | HTTP | 说明 |
|---|---|---|
| 1001 参数错误 | **400** | 含 FastAPI 的 `RequestValidationError`（响应体带 `data.errors` 明细）与业务参数错误（如"该用户名已被注册"） |
| 1002 未登录 | **401** | 无 token、token 过期/伪造 |
| 1003 权限不足 | **403** | 仅用于与资源归属无关的越权（见 6.8） |
| 2001 资源不存在 | **404** | 含"存在但不属于你"，不区分（见 6.8） |
| **3001 AI 调用失败** | **200** | **刻意保持 200**：外部依赖抖动的业务结果，前端按 `code` 提示重试（7.6） |
| 5000 服务器内部错误 | **500** | 细节只进日志（14.6） |

其余：`HTTPException` 保留原始状态码并按 `HTTP_STATUS_TO_CODE` 映射业务码；未捕获异常 → 500 + 5000。

**为什么偏离"全部 200"**：全 200 会让浏览器、Nginx、Electron 客户端、curl 和监控都分不清「业务失败」和「服务挂了」；未登录必须是真 401，否则任何标准中间件与前端拦截器都会失效。业务语义仍由信封 `code` 表达，HTTP 状态只表达传输层。

**为什么必须有这张表（而不是各处自己传 status_code）**：同一业务码在代码里有"裸构造"与"便捷构造"两种写法。项目里曾出现过 `.not_found()` 抛是 404、裸构造 `BusinessException(ErrorCode.NOT_FOUND, ...)` 抛是 200，以及未登录在部分路径返回 200 —— **同码不同状态**，前端表现为"偶发跳不过登录页"，极难排查。把推导收进 `__init__` 后，23 处裸构造与便捷构造自动一致。

**前端配套**：axios 拦截器**两条路径都要解信封** —— 成功路径按 `code` 判错（覆盖 3001 这类 200 业务失败），错误路径读 `error.response.data`（覆盖 400/401/403/404/500）。

## 3. 契约与表结构

### 3.1 SSE 流式对话 [已决策]

```
POST /api/v1/chat/conversations/{conversation_id}/stream
Body: { "content": "...", "client_msg_id": "<uuid>" }
Response: text/event-stream
```

- 具名事件：`start → delta* → tag? → done → end`，异常时 `error`，幂等命中时 `pending`；每个 `data` 都是一层 `{code,message,data}` 信封。
- 流末尾固定 `event: end` + `data: [DONE]`。
- 保留 `GET .../stream?content=...` 作**调试用**（curl / 手册 8.4 兜底），前端不调用。
- 完整契约见 `backend/README.md` §4.6。

### 3.2 `messages` 表补列 [已决策]

手册 5.3 的 `messages` 只有 `id / conversation_id / role / content / created_at`，**缺前后端契约必需的幂等字段**：

```python
client_msg_id: Optional[str] = Field(default=None, max_length=64, index=True)
# + 唯一索引 (conversation_id, client_msg_id)
```

**为什么必须补**：设计文档 4.3 要求"同一 `client_msg_id` 重复提交不得产生两条用户消息 + 两次 AI 回复"（断流重试场景）。曾用 HTML 注释内联在 `content` 前缀实现，**已废弃**——那个标记会跟着 `MessageResponse` 发给前端，污染用户可见文本、长度统计与搜索。数据库尚未建立，现在改的成本是零。

### 3.3 `conversations` 表补列 [已决策]

手册 7.7 要求"连续追问同一方向不超过 3 轮"，但 5.3 没有任何字段承载这个计数。追问轮数是**会话级状态**，不属于单条消息：

```python
followup_direction: Optional[str] = Field(default=None, max_length=50)  # 当前挖掘维度
followup_round: int = Field(default=0)                                  # 同方向已追问轮数
```

判定规则：每轮从 `profile_extract` 抽出的标签里取主导 `dimension`；与 `followup_direction` 相同则 `+1`，不同或为空则重置为 1；达到 3 轮时下一轮在 Prompt 里注入"必须换维度"的指令。抽不到标签时保持原值，不清零。

> **[后续推翻：本节已作废]** 用户随后明确要求删掉这套「同一方向追问 3 轮后换维度」的机制
> （原话："可以把之前确认的三次换个目标继续挖的代码删掉了，要保证代码都是有用的"）。
> 两列、计数逻辑、Prompt 硬约束、SSE 字段**全部已移除**，真实库里这两列也已用
> `backend/scripts/drop_followup_columns.py` **物理删除**（先备份再 `ALTER TABLE ... DROP COLUMN`）。
> 详见 3.3 的后续状态与手册 7.7。**注意：11.9 面试的「每题后追问 1-2 轮」是另一件事，未受影响。**

### 3.4 5.2 有表、5.3 无字段 [已决策]

`interview_questions`、`test_results` 在 5.2 表清单里，但 5.3 没给字段表 → 按语义补齐，字段以 `backend/app/models/` 为准，待你复核后回写手册。

## 6. 前后端并行开发的集成对账

前后端是并行搭的骨架，接口对账时发现以下问题，全部已修。**根因是「设计文档要求的接口」与「手册 10.2 的接口」不一致，两端各自按不同来源实现。**

### 6.1 列表响应形状不匹配（影响最大）

后端所有列表端点的 `data` 是**裸数组**（`ApiResponse[List[X]]`）；后端虽然定义了 `PageData`，但**一处都没使用**。前端按设计文档 5.4「列表接口统一 `page/page_size/total`」的约定，有 7 处读 `.items`，运行时恒为 `undefined` → **所有列表恒为空**。

**决策**：前端加 `normalizeList()` 统一收口，两种形状都吃；**分页暂不在后端实现**。手册 10.2 的列表端点本来就没有分页参数，等数据量上来（任务/对话历史变长）再按 5.4 补。

### 6.2 幽灵接口（前端调用了不存在的路径）

前端 api 层曾有 12 处路径后端不存在（会 404），全部改前端：

| 曾调用 | 实际 |
|---|---|
| `POST /auth/logout` | 无此端点 → 删除（登出是纯客户端行为） |
| `POST /resumes`、`POST /resumes/upload` | `/resume`、`/resume/upload`（**单数**） |
| `GET /tasks` | `/task`（**单数**） |
| `POST /interview/sessions` | `/interview/start` |
| `GET /report/growth` | `/report` |
| `PATCH /profile` | `POST /profile/feedback` |
| `GET /test/intro` | 无此端点 → 引导页文案改前端静态 |
| `GET /interview/options` | 无此端点 → 模式/场景改前端常量 |
| `GET /daily/history` | 无此端点 → 页面走空态 |
| `GET /home/summary` | 无此端点 → 临时并行组合 4 个接口；**已决定后端补实现**（见 6.6） |
| `POST /events` | 无此端点 → 临时降级为本地 no-op；**已决定后端补实现**（见 6.6） |
| `/chat/stream` | 无此端点 → 删除兜底，`conversationId` 改必填 |

**教训**：后端严格照手册 10.2 实现（37 条路由），前端照设计文档 5.4 实现，而 5.4 里有 4 个接口（`/home/summary`、`/events`、`next_action`、分页形状）**手册里根本没有**。以后新增接口必须先落到手册或勘误文档，再让两端各自实现。

### 6.3 SSE 会话生命周期隐患

`StreamingResponse` 的 body 在请求依赖被清理**之后**才被消费。若在生成器里沿用 `Depends(get_db)` 的请求级 Session，保存 assistant 消息、写画像标签都会作用在**已关闭的 Session** 上。已改为生成器内 `SessionLocal()` 自开自闭，并且只把 `user_id`（纯数据）传进生成器，避免 `DetachedInstanceError`。

### 6.4 漏斗判据失效

`GET /profile` 走 `get_or_create_profile`，**永远返回一个画像对象**，因此"新用户没有画像"这个状态无法用"对象是否存在"判断，「已登录 + 无画像 → `/test/intro`」的漏斗永远不触发。

**决策**：`ProfileResponse` 增加 `tested: boolean`（依据 `test_results` 是否存在）。**判断"有没有画像"一律看 `tested`，不要看对象是否存在。**

### 6.5 幂等标记不能藏在消息正文里

`client_msg_id` 曾以 HTML 注释 `<!--cmsg:xxx-->` 内联在 `Message.content` 前缀——这个标记会跟着 `MessageResponse` 一起发给前端，污染用户可见文本、长度统计与搜索。已改为正式列（见 3.2）。

### 6.6 补实现的两个接口 [已决策]

设计说明书 5.4 提出、手册 10.2 没有的两个接口，用户拍板 **M1 联调前补上**：

| 接口 | 用途 | 关键约定 |
|---|---|---|
| `GET /api/v1/home/summary` | 首页一次请求拿全（阶段、画像、标签、今日一问、AI 发现、进行中任务、`next_action`） | 替代前端 4 个并行请求；`next_action` **由后端按阶段+画像+任务状态判定**，前端不做推荐逻辑 |
| `POST /api/v1/events` | 行为埋点上报（`test_skip` / `task_abandon` / `advice_ignore` / `daily_answer` / `chat_round`） | 兼容单条与批量两种 body；**只落结构化日志，不建表** |

**`next_action` 为什么必须由后端给**：它是"AI 主动性"这个核心卖点的落点（手册 1.2）。如果让前端自己按几个 if 排序，这个卖点就退化成了静态导航。规则先写死在 `home_service.py`，后续可替换为 AI 生成。

**埋点为什么不建表**：手册 5.3 没有事件表，擅自建表属于范围扩张。当前只写日志；要做行为分析需新增 `events` 表并回写手册 5.3。

### 6.7 安全修复：`/uploads` 不能做无鉴权静态目录 [已决策]

骨架初版在 `main.py` 里把 `uploads/` 挂成了 `StaticFiles`，于是**未登录的人只要知道路径 `GET /uploads/resumes/{user_id}/{uuid}.pdf` 就能下载别人的简历**。简历含姓名、手机号、学校、经历，属 PII；`resumes.file_path` 里还带 `user_id`，遍历 UUID 即可。

违反手册 **14.5 权限**（用户只能访问自己的数据）与 **14.1 数据保密**。

**修复**：删除静态挂载，改为鉴权端点 `GET /api/v1/resume/{id}/file`，越权一律按"不存在"（`2001`）处理，不回 `1003`（避免泄露 id 是否存在），并做目录穿越校验（规范化路径必须仍在 `UPLOAD_DIR` 内）。上传侧同时收紧：扩展名白名单 `.pdf`/`.docx`、10MB 上限、落盘用 `{uuid}.{ext}` 而非原始文件名。

### 6.8 越权一律返回「不存在」，禁止用 1003 当 oracle [已决策]

修 `/uploads` 漏洞时发现的同类问题：`GET/PUT /resume/{id}`、`/{id}/optimize`、`/{id}/report` 在「资源存在但不属于当前用户」时返回 **1003 权限不足**。攻击者据此可以枚举出「哪些 id 是真实存在的」。

**决策（编码规则，所有私有资源端点都必须遵守）**：

> 查私有资源时，「不存在」与「不属于你」必须返回**同一个**错误码 `2001`；禁止用 `1003` 区分。否则错误码本身就是可枚举的 oracle。

适用范围：`resume`（`{id}` / `optimize` / `report` / `file`）、`task`（`{id}` / `abandon` / `steps/{id}/complete`）、`interview`（`questions` / `answer` / `finish` / `review`）、`chat`（`conversations/{id}` 下的 `messages` / `stream` / `conclusion`）。

`1003` 只保留给「与资源归属无关的越权」（如将来的管理员接口、被封禁用户），当前业务里没有这种场景。

### 6.9 `stage` 字段全接口统一为「slug + label」[已决策]

同一个概念出现两种编码：`GET /home/summary` 返回英文 slug（`explore`/`prepare`/`sprint`），而 `GET /profile`、`GET /test/result` 返回中文（`探索期`/`准备期`/`冲刺期`）。这种分叉迟早出错。

**决策**：全接口统一——`stage` 一律为**英文 slug**，另加 `stage_label` 为中文展示名；枚举固定 `explore` / `prepare` / `sprint`，未知值兜底 `explore`。数据库列内存储的编码在 README 注明，转换只发生在 schema 层，不为了改接口去改存量数据编码。

### 6.10 面试追问：手册没定义判别字段 [已决策]

手册 11.9 只说"每题后 1-2 轮追问"，**没有定义 `POST /interview/{id}/answer` 的响应如何区分"这是同一题的追问"和"这是下一道新题"**。前端只能靠猜，且实现里确实缺字段。

**语义定案**：追问 = **同一道题的再问，不新建题目行**（都挂在同一行 `interview_questions`：主问题答 `answer`，追问存 `followups` JSON 数组）。补判别字段 `action: "followup" | "next_question" | "finished"`，追问时 `question_id` 与上一题相同，前端据此**就地续问而不是追加新题**；追问上限 `MAX_FOLLOWUP_PER_QUESTION = 2`。

**顺带修掉两个实现 bug**（都是读代码发现的，跑起来未必报错）：

1. 判断"这次答的是不是追问"用了 `extra["kind"] == "followup"`，但该字段出题时写死 `"main"`、之后从未被置为 `"followup"` → **主问题的回答会被第二次作答覆盖，`followups` 永远为空**。已改为以「是否有待答的 `extra["followup_question"]`」为唯一真源。
2. `followups` 从未回传、追问句藏在 `extra` 里 → 前端根本看不到追问内容。

**附带的编码约定**：JSON 列**只做整体赋值，不做就地修改**（`extra = dict(...)` → 改副本 → 整体赋回）。SQLAlchemy 默认不追踪 JSON 列的内部变更，就地改 flush 不出 UPDATE——这是 `MutableDict` 存在的原因。

> **已实测证实**（装好 Python 后用探针脚本在 SQLite 上验证）：`tag.extra["evidence"] = "就地修改"` 提交后读回**仍是旧值**（静默丢失）；改成整体赋值后读回新值。同理 `UNIQUE (conversation_id, client_msg_id)` 确实被 SQLite 强制执行（重复插入抛 `IntegrityError`）。全仓库 grep `.extra[...] =` / `.followups.append(` 等就地修改模式，**只命中一处解释性注释，无真实违规**。

### 6.11 数据库由 PostgreSQL 改为 SQLite [已决策]

用户拍板：**PostgreSQL 换成 SQLite**。原因是本机既没有 PostgreSQL 也没有 Docker，联调根本起不来；SQLite 能让后端真正跑起来并被验证——在此之前后端 81 个 `.py` 全是"读得通、没跑过"。

**影响面**（远比"换个连接串"大）：

| 项 | 处理 |
|---|---|
| JSONB 列（`extra` / `conclusion` / `parsed_data` / `report` / `options` / `content` / `condition` / `followups` 等） | `JSONB().with_variant(JSON(), "sqlite")`，PostgreSQL 仍走 JSONB，SQLite 退回通用 JSON；**不要在模型里散写 `JSONB`** |
| PG 专有类型（`postgresql.UUID` / `ARRAY` / `INET`） | 换 SQLAlchemy 2.0 通用类型 |
| JSON 路径查询（`->` / `->>` / `@>`） | 能改 Python 侧过滤的就改，改不了的标注为 SQLite 下不可用 |
| 并发 | `connect_args={"check_same_thread": False}`，否则 FastAPI 多线程下必然报错 |
| Alembic | `render_as_batch=True`（SQLite 的 `ALTER TABLE` 能力弱） |
| 时区 | SQLite 无真正时间类型，`DateTime(timezone=True)` 退化为字符串，需确认无逻辑依赖时区语义 |
| 生产 | 保留 PostgreSQL 路径（配置可切回），`psycopg2-binary` 变为可选依赖 |

**附带**：手册 2.1 / 2.3 / 5.1 / 16.2 的 PostgreSQL 条款待回写；JSONB→JSON 后仍要遵守 6.10 那条「只整体赋值、不就地修改」的约定（SQLAlchemy 在 SQLite 下同样不追踪 JSON 内部变更）。

### 6.12 运行期发现的缺陷（**只有真跑才会暴露**）

装上 Python 3.12 并把后端真正跑起来之后，逐一暴露的问题。它们**全部**通过了此前多轮"静态自检 100+ 条断言"，包括"217 条 import 的模块与符号全部解析成功"——那类断言验的是文本模式，验不了语义。

## 9. 用户验收后新增的决定与踩过的坑

### 9.1 奖章从 1 枚扩到 3 枚（**推翻手册 1.5「砍掉奖章墙」**）

手册 1.5 明确写过"P1 只保留一个轻量奖章（完成第一个任务），砍掉奖章墙"。用户看到界面后要求"添加其他奖章，建议一共三个，后续可以添加"，因此改为三枚，并要求视觉"大一点、华丽一点"。

| key | 名称 | 条件（**必须由真实证据驱动**） |
|---|---|---|
| `first_task` | 起步行动家 | 已完成任务数 ≥ 1 |
| `five_steps` | 坚持打卡者 | 累计打卡步骤数 ≥ 5（跨任务累计） |
| `profile_shape` | 方向初现 | 画像标签数 ≥ 6（标签是 AI 从真实对话里抽出来的，不是用户自报） |

工程上的两个要点，回写手册时要保留：

1. **种子里有、引擎里没有 = 死数据**。`seed_data.BADGES` 早就写了两枚，但 `badge_service` 只认第一枚，于是「坚持打卡者」从来没被发放过。现在三枚的定义只有**一个来源**（`badge_service.BADGE_RULES`），`seed_data.BADGES` 由它派生。**凡是"种子/配置/代码"三处各写一份的定义，都要收成一个来源。**
2. **事件只是触发器，一次触发要评估全部条件**。原来按 `event == "task_completed"` 分派，新增奖章时老用户永远不会被追认。改成任何触发都重算全部条件 + 每小时 `settle_badges` 兜底。另外打卡路径原本**根本没有**触发奖章检查（打完第 5 步要等一小时），现已接在 `task_service.complete_step`。

`GET /badge` 的返回从"裸数组（只含已获得）"改成 `{total, obtained_count, items[]}`（每项含 `key/name/description/hint/obtained/obtained_at/progress`）。**界面要显示"还差多远"，就必须返回未获得的那几枚**，只返回已获得的做不出这个界面。

### 9.2 `POST /task/generate` 必须服务端去重

同一个痛点连点几次「生成任务」会攒出同题任务（实测 `admin` 7 条里有 2 对）。只把 `existing_tasks` 塞进 prompt 靠模型自觉是不够的。现在服务端按**标题相似度**（`app/utils/similarity.py`，bigram Jaccard，阈值 0.6）与已有**进行中**任务比对，命中则**不新建**、返回已有任务并给 `reused=true`（`TaskGenerateResponse`）。

边界（回写时要保留）：**只跟「进行中」比**（放弃/完成后想重做是合理的）、**按标题而不是按痛点比**（同一痛点下可以有很多件不同的事，按痛点去重会让用户再也拿不到新任务）。

### 9.3 SQLModel 的 `Task`/`TaskStep` 没有 `relationship()` → 不能用 ORM 删 task

`db.delete(task)` 会撞 `FOREIGN KEY constraint failed`：工作单元不知道两张表的依赖顺序，把 `DELETE FROM tasks` 排到了 `DELETE FROM task_steps` 之前。删任务必须显式按"子表先于父表"发 Core `delete()`。

### 9.4 改 prompt（`.txt`）不重启就不生效

`app/ai/parser.py` 的 `load_prompt` 是 `lru_cache`，而 `--reload` 默认只监听 `.py`。**这个坑前后咬了两次**（开场白调性一轮、任务生成一轮），表现为"改了 prompt 但输出没变"，很容易误判成 prompt 写得不对。已在 `dev-backend.ps1` 与两个 README 的启动命令里加 `--reload-include '*.txt'` 从根上堵掉；用别的方式手起 uvicorn 时仍要手动重启。

### 9.5 不要用"登记式簿记"记录渲染状态

会话页的开场白曾经用 `openingMessageIds: Map<会话, 消息id>` 记录"这条开场白已经渲染过"。因为**登记发生在丢弃之前**，切走时会话被永久毒化：`loadMessages` 按这个 id 把服务端真实存在的开场白过滤掉、`ensureOpening` 又因为"已经有开场白"提前返回 —— AI 的提问凭空消失且不可自愈。现在参与判断的字段全是**渲染态本身**（`messages` 里有没有 `client_msg_id === 'sys:opening'` 的消息）。

**纪律**：任何"记录某个东西已经渲染过/已经处理过"的副本，都必须能由渲染态推导出来；推导不出来就不要存。两次会话页 bug、一次奖章种子 bug，都是同一个形状。

### 9.7 新会话 = 用户想换话题（"新对话 4 继承了新对话 3"）

用户报："对话四继承了对话三，并且我认为新建对话就是用户自己想切换聊天内容了。"
dump 是：会话 3 里用户说『健身，刷视频，看短句』→『写，会写日记之类的』，
新建的会话 4 开场白却是"嗨，你平时健身都练点啥呀"。

**根因**：上一轮为了"跨会话不许重问同一件事"，把**用户最近说过的话**当成了
"可以拿来发问的**素材**"注入开场白 Prompt（`{"用户已经答过的话（不要重新确认状态…）": [...]}`），
于是模型顺着这些素材提问。

**定案（三条一起改，缺一不可）**：

1. 跨会话信息**只有一个语义 —— 已经聊过、禁止再提**；它在开场白 Prompt 里绝不再出现在
   "素材/候选"位置，而是明确写成「**已经聊过 = 禁止再提** …… **不是**可以拿来发问的素材」的点名清单；
2. 服务端**机械保证**（不只靠 prompt）：`_drop_already_asked()` 的 `asked` 除"最近 N 条
   开场白"外，**并入用户最近说过的话**（复用同一个 `_looks_referenced()` 判定），
   刚聊过的话题对应的画像标签 / 任务会被从候选里剔掉 —— 模型就算想顺着问也没有素材；
3. `chat_opening.txt` 补一条硬规则（与原有"不许重问 / 换个说法也算重复"**合并成同一条**，
   不写成两条互相打架的规则）：新会话意味着用户想换一个话题，列过/聊过的一律不许再提、
   也不许当铺垫，要问一件和它们都无关的事。

**不许改坏的边界**：全新用户照旧只聊日常；有背景且背景**没有**刚聊过时，仍然必须真的引用背景
（"最常见的错误是明明有背景却问'最近在忙什么'"那句规则继续成立），只是不许引用最近刚聊过的那部分。
真实 API 实测（会话 1 说两句 → 会话 2/3/4 开场白全部为日常小事、命中旧话题关键词 0；
回归：全新用户走日常、有背景无近期会话仍引用背景、同一会话连调两次幂等）见
`backend/README.md` §4.16.6 与 §5.1.1。

#### 9.8.4 「只聊天不打卡」到底发生了什么（一句话）

**方案甲 · 标签数量 + 覆盖维度数封顶加分**（例：最多 +15）

### 9.11 「没有的事情坚决不许杜撰」—— 硬规则（用户要求）[已决策]

用户原话：

> **"你上次说帮同学修电脑，那次是哪出问题？"没有的事情坚决不要杜撰，要严厉禁止这种事情**

**触发这次要求的是一个真实事故（我犯的）**：我在给用户举例说明"把标签里的 `extra.evidence` 喂给 AI 会怎样"时，写了示例开场白「你上次说帮同学修电脑，那次是哪出问题？」。这句里有两处是编的：① "帮同学修电脑"来自某次验收时**探针账号的测试文本**（agent 自己编的假输入），不是用户真实数据；② 更要紧的是「**那次是哪出问题**」——"出了个故障"这件事用户从没说过，是模型（和我）把素材加工成了一个**新事件**。

**两层落地**（缺一不可）：
1. **Prompt 层**：`chat_opening.txt` 第四步 + `chat_system.txt` 规则 13/14。硬规则：素材里没写的**时间/地点/人物/数量/频率/事件/原因/故障/结果**一个字都不许补；不许把素材加工成新事件；不许把用户没说过的事说成"你之前说过/你上次提到"。**反例直接用上面这个真实事故写进 prompt**（比抽象规则有效）。
2. **机械保证（开场白）**：开场白改成结构化输出 `{text, used}`，`used` 必须**原样抄**素材字符串；服务端 `_validate_opening()` 逐条核对：`used ⊆ materials` → `text` 必须真的提到所申报的素材 → **`used` 为空却在陈述用户事实**（26 条引导语："你上次/你说过/你提过/你会/你负责…"）也判杜撰。不合格 → warning 留痕（素材清单 + 模型原文 + used）→ 换本地模板。**校验纯本地、不额外调 AI**；坏 JSON 有 `default` 兜底，实测四档坏格式全部 HTTP 200 零 500。

**启发式的取舍**：假阳性 = 换成模板（只是措辞变固定），假阴性 = 用户看到自己从没说过的事（信任级事故）。所以**偏保守**，`"你平时……"`这类纯习惯性问法刻意不入词表。

**已知边界（不许粉饰）**：
- **对话正文是 SSE 逐字流式，没有机械保证**，只有 prompt 规则。要上机械检查只能等整段生成完做事后校验，而那时话已经显示给用户（或改成"生成完静默、校验通过再一次性推"的伪流式），代价见 `backend/README.md` §4.16.8。
- `used` 是**模型自报**的：它能引用素材 A 的同时补一句细节（"看短句" + "你每天都看"），这道检查覆盖"申报↔素材、申报↔话"的一致性，**不覆盖句子里每个细节**。

### 9.12 AI 挖不深：L1 / L2 已批准，L5 未批准 [已决策]

用户对 9.10 里列出的三条逐条表态：

| | 内容 | 决定 |
|---|---|---|
| **L1** | 让 AI 看见用户**原话**（`extra.evidence`），开场白从复述标签变成像人提问 | **批准**。附加要求：**"对话一定要向这样充满人的味道，要让用户有和人在对话的感觉"** |
| **L2** | `chat_system.txt` 加"往具体里挖"的硬规则（禁止"还在弄吗"这类是非题，顺着同一件事追 2-3 层更深细节） | **批准**。"这是解决问题不够深的一步" |
| **L5** | 把**已完成任务 / 简历经历**也纳入开场白素材池 | **未批准**（用户没提），**不做** |

**L1 的前置修复（我在派单前 dump 真实数据时发现的）**：`extra.evidence` 里存的"用户原话"**有一部分是 AI 自己说的话**，真实样本：`能力/学习 = "会Java和C，说明你编程底子不算白纸"`、`兴趣/产品 = "AI：你之前提过对技术/产品有点兴趣"`、`痛点/缺项目 = "有没有做过完整的小项目？"`（AI 的问句）、`焦虑/中 = "比空焦虑强多了"`。若直接喂进 prompt，AI 就会说「你上次说"有没有做过完整的小项目？"」——**把 AI 的话安到用户头上**，正是 9.11 要禁的那类杜撰。所以 L1 必须**先修来源（证据只能取 `role="user"` 的消息文本）**，再在**读侧加一道机械过滤**（evidence 必须能在该用户自己发过的消息里原样找到，找不到就不许进 prompt 并留日志）。存量脏数据不做原地修改，靠读侧过滤挡住即可。

**另一个已知事实**：带原话的标签**全部来自聊天**（真实库 35 条标签里 24 条有原话，来源全是 `chat`；`test`/`daily`/`task` 来源的标签**没有原话**）。所以 L1 对"刚做完测评、还没聊过"的账号没有效果 —— 这是产品意图（画像是聊出来的），不是 bug。

### 9.14 一个会让人误判"改了没效果"的工程陷阱：`.env` 是相对路径 [纪律]

`app/core/config.py` 的 `SettingsConfigDict(env_file=".env")` 是**相对当前工作目录**的。因此：
- **从 `backend/` 目录**跑脚本/起服务 → 读到真 Key，AI 正常工作；
- **从仓库根目录**跑脚本 → 静默用占位 Key `sk-xxxxxxxx` → DeepSeek 返回 401 → 代码按"AI 不可用"**走 6.6/7.6 兜底模板**，**不报错、不提示**。表现就是"我改了 prompt 但输出没变"，很容易误判成 prompt 写错了。

**纪律**：任何临时脚本、任何手工起服务，**先 `cd backend`（或用 `workdir=backend`）**。这一轮有 agent 真的踩了（第一次起探针全走兜底模板），值得写下来。

### 9.15 成长任务：能删、能清、能真的生成新的 [已决策]

用户连着报了三件事，其实是同一条链上的三个缺口：

**① 「成长任务没有删除按钮」**
实情比"忘了加按钮"复杂三层：后端**只有"放弃"（`POST /task/{id}/abandon`，改 status）没有删除**；"放弃"只藏在**详情页**；而且**列表接口不按状态过滤**，所以放弃之后任务**仍然留在列表上** —— 用户怎么都清不掉。

落地：新增 `DELETE /api/v1/task/{task_id}`（越权/不存在 → 2001），硬删除任务 + 其 `task_steps`（**必须显式按"子表先于父表"发 Core delete**，SQLModel 没有 `relationship()`，`db.delete(task)` 会撞 FK —— 这个坑踩过两次了）。列表页与详情页都能删。

**删除的后果必须说清，因为它是真的**：`action_score` 就是"数你打过卡的步骤"算出来的。实测删一条"5 步里打过 2 步卡"的任务：
```
action_score 16.0 → 0.0     total_score 30.6 → 25.0     阶段：准备期 → 探索期
（删一条一步没打卡的任务：三个数一个不变）
```
所以确认弹窗**先拉一次详情把打卡数数准**（不猜），再分四种情况说人话：没打卡（不影响分数）／有 N 步打卡（**分数会下降**）／已完成（额外说明"完成整条任务的加分也会收回"）／详情拉不到（保守说法）。并提示"只想让它别再出现在待办里，用「放弃」也一样，而且不会掉分"。
**删完必须在同一事务里调 `profile_service.recompute_stage(..., commit=False)`**（打卡路径用的同一入口，也是全项目唯一写 `action_score/total_score/stage` 的地方）—— 否则分数会停在旧值直到用户下次打卡。

**② 去重没拦住"同一个小工具的两个说法"**
用户连点两次生成了「用 Java 做一个健身打卡命令行小工具」与「用 Java 做一个健身动作计数器命令行小工具」，两条都被留下。他确认**这两条应该被拦住**。

`is_similar()` 改成**三条同时成立**（`app/utils/similarity.py`，唯一判定入口，`task_service` 与清理脚本都跟随）：
```python
CANDIDATE_SIMILARITY_THRESHOLD = 0.43   # 条件1：bigram Jaccard 粗筛
MIN_COMMON_SUBSTRING = 6                # 条件2：归一化后最长公共子串 ≥6
MIN_CONTAINMENT_LENGTH = 4              # 条件2.5：短标题整个是长标题的连续子串（补短标题漏判）
PROTECTED_LANGUAGE_TOKENS = (Java, Python, C++, C#, C, Go, JS, TS, Rust, Kotlin)  # 条件3a
PROTECTED_TOPIC_TOKENS    = (健身, 记账, 通讯录, 简历, 面试, 职业, 技术)          # 条件3b
```
判定 = ［条件1 ∧ 条件2］**或** 条件2.5，再 ∧ 非条件3。

**条件3 后来又被放宽过一次（这条也是用户拍板的）**：保护词必须**拆成两组**，因为它们语义不同 ——
- **主题词**（健身/记账/…）：仍是"只出现在一侧即冲突"（**语义冻结，不许顺手改**）；
- **语言名**：改成「**两边都提了语言、且没有共同语言**才算冲突」。
  用户原话：**"带不带语言前缀不算两件事"** —— 于是 `做一个健身打卡小工具` 与 `用 Java 做一个健身打卡命令行小工具` 判为重复；而 `用 Java…` vs `用 C 语言…`（都有语言且无交集）仍判不重复，`用 Java…` vs `用 Java 和 Python…`（有共同语言）不冲突。
  另外**顺带修掉一个既有 bug**：语言名原先按裸子串匹配，`C` 会命中 `C++`/`C#`，导致「用 C 做通讯录小工具」与「用 C++ 做通讯录小工具」被误判为重复（实测 Jaccard=1.000）。现在按**词边界**匹配（左右不紧贴 `[A-Za-z0-9_+#]`），`Java` 也不再命中 `JavaScript`。
  实现注意：`has_conflicting_protected_token()` 现在吃**原始标题**（内部自行归一化）—— 因为 `normalize()` 会把 `C++`/`C#` 压成 `C`，语言名必须回到原始文本才分得清。
  已知边界：语言词表只覆盖 10 个，`PHP`/`Swift`/`Node.js`/`Vue`/`SQL` 等不在表内（后果是"不算冲突"，偏向合并）；清理脚本内部仍传归一化 key，故它那条路径上 `C/C++/C#` 的区分会丢失（改前同样丢失，非本轮引入）。

**短标题漏判**（收尾时发现）：`做一个健身打卡小工具` vs `做一个健身打卡工具` 曾判"不重复" —— `normalize()` 抽掉"小工具/命令行/做/一个"后只剩 4 个字「健身打卡」，而条件2 要求连续 6 字，**短标题在数学上不可能满足**（连与它自己都不判重复）。修法是加**包含判定**（条件2.5），而**不是**调低 `MIN_COMMON_SUBSTRING` —— 实测「技术方向/职业方向」那对的 LCS 恰好 = 4，降到 4 会立刻误合并。
**为什么不是单纯把 0.6 调到 0.43**：漏网案例实测 Jaccard=0.438，而**"职业方向/技术方向"这对真不同的任务实测 0.400** —— 两者重叠，单降阈值必然误杀。所以条件1 只做粗筛，真正的判据是条件2（同题重复会留一条长连续片段），条件3 再挡住"换语言/换主题词"（例如 `用 Java 做…` vs `用 C 语言做…` 实测 0.462、LCS 7，两条都过，但换语言是两件事）。
**注意两个实测教训**（我最初手工估的都被推翻了）：a) 我拍"公共子串 ≥8"，实际基准案例只有 **6**（`normalize()` 会把"命令行/小工具/做/一个"整段抽掉，公共片段被切断），门槛设 8 会把要抓的案例重新漏掉；b) 光靠"两个条件"会新增误杀，所以必须有条件3。

**③ 「这样就生成不了新任务了」——去重只拦不换方向，功能就变成空转**
去重一旦命中就直接复用，而模型被同一批素材（痛点=缺项目 + 画像里的"健身/Java"）困住、只会吐变体 → 用户连点几次都只得到"已经有一个类似的任务了"。**这是去重的副作用，不是去重错了。**

落地：`generate_task()` 命中重复时**再调一次模型**（最多 1 次），把撞上的标题 + 完整"进行中"清单点名给它，要求换主题/换产物形态、实在没有就换痛点维度；重试仍撞才回到"复用 + `reused=true`"（契约不变）。只在撞车时付成本：正常一次 ≈3.6–4.1s，撞车重试 ≈8.2–8.3s（2 次调用）。同时 `task_generate.txt` 新增规则 10「**什么才算新任务**」：只改措辞、换语言、加/去前缀、换量词、换个工具名**都不算**；**主题词相同（都围绕"健身"）就算同一条**；这个痛点做完了就换痛点维度。

**④ 收尾时又发现一个漏洞（短标题漏判）**：`做一个健身打卡小工具` vs `做一个健身打卡工具` 判"不重复" —— 归一化后只剩 4 个字「健身打卡」，而条件2 要求连续 6 字，**短标题在数学上不可能满足**。修法是加一条**包含判定**（短的那条整个是长的那条的连续子串且足够长 → 判重复），而不是继续调低 LCS 门槛（那会重新打开"职业/技术"的误合并）。

**这一串的通用教训**：**"拦住重复"和"还能生成新东西"是一对约束** —— 只做前者，功能会退化成每次只回一句"已经有了"。凡是加"去重/拦截"这类规则，都要同时想清楚**被拦下之后用户还能怎么办**（这里就是"重试换方向"）。

### 9.18 「一次都没碰过的空条目不算没填」—— 润色提示的口径 [已决策]

**用户要求**（我提出后他说「**两个都改**」）：改成"**用户一次都没碰过的空条目不算没填**"。

**问题**：`MyResumePage` 给每个可重复板块（教育背景 / 项目经历 / 校园与实践经历）默认摆**一条空条目**当入口（`writeEmptyEntry`，不摆就没有"从哪开始写"的地方）。后端的 `_empty_field_labels()` 把这条空条目当成"用户写了、但字段没填全"，于是**所有不打算写校园经历的人**，润色后都会被告知：

> 已润色；还有 7 项你没填，先空着（校园与实践经历的名称、你的角色、起止时间、情境、任务等 7 项）

这不是"没填"，是"**没打算填**" —— 一条不会消失的假提醒。

**口径（改法）**：`_empty_field_labels(..., skip_untouched_sections=True)`（只给"已润色"那条 message 用）：

- 可重复板块**先丢掉整条全空的条目**（`fact_guard.is_blank` 递归判空：整条都没内容才算空）；
- 剩下的条目**一条都没有** → 这一节**一个字都不提**（用户没碰过）；
- 只要用户**碰过**这一节（哪怕只写了名称），这一节里仍然空着的字段**照旧逐条提示**（"项目经历的情境、任务…"）—— 提示的是"你开了个头，这几项还空着"。
- **全空短路那条路径（`polish_resume` 里"你还没填任何内容"）不开这个开关**：那时用户什么都没填，就该把 27 项要填的**全都列出来**（否则那句话会变成"要填的有：姓名、年级…"却漏掉三个板块）。

**连带改了一句文案**：`模板里的字段你都填了` → **`你写到的字段都填全了`**。
因为整节没碰过的板块被 skip 掉了，而**完整度那边它仍然算 0 分**（权重 100 里校园与实践经历占 10 → 不填这一节，完整度封顶 90，画像 `resume_score` 也跟着低）。"你都填了"与"才 90 分"会自相矛盾。

**完整度为什么**不跟着改（明确记录，不是漏改）：「完整度」量的是**这份简历填了多少**，跳过一整节就是没那么完整，扣掉那 10 分是对的。若改成"只按用户碰过的板块算比例"，一个只填了姓名的人就会得到 100 分 —— 那才是错的。

**验证**：4 组构造数据（全填了但校园整节没碰 / 只填姓名 / 项目只写了名称 / 全空）逐一核对条数与标签；再真机跑一次 `POST /resume/polish`（真 Key）→ message 实测为 **「已润色；你写到的字段都填全了」**。探针账号当场清理；**用户自己保存的那份简历（admin / 我的简历 / 目标岗位前端开发）一行未动**。

### 9.20 润色太浅：**技能栏允许展开**成能力表述（唯一例外）[已决策]

**用户原话**：「**简历润色没有完成，只是简单润色一下，例如写道 Java 可以润色为「熟悉 Java 基础语法、面向对象编程（封装、继承、多态）、集合框架、异常处理、IO 流。能使用 Java 独立完成控制台程序开发。」这种润色**」。

**问题**：原来的润色对技能只做"规范写法"（`vue` -> `Vue`），用户写「Java」出来的还是「Java」——他填了关键词，看到的却不是一个能放上简历的表述。这是 9.11「不许杜撰」被**过度外延**的结果：把"不许编经历"执行成了"技能也不许展开"。

**决定：技能（`skills`）是唯一允许"展开"的字段。** 关键词 -> 一句能力表述，并且**那个技术名必须留着**。

**四条不许（写进 prompt）**：① 不许引入用户没写过的其它**技术名 / 工具名 / 框架名 / 库名 / 证书名 / 公司名 / 项目名**；② 不许出现任何**数字**（年限、项目数、人数、百分比、评级）；③ 不许写"精通 / 资深 / 专家 / 多年经验"，只用"熟悉 / 掌握 / 了解 / 能使用…完成…"这类与在校学生相称的措辞；④ 不许写成一大段 —— **每条 1~2 句**：第一句「熟悉 X + 这门技术的常见能力点」，第二句「能使用 X 独立完成 ……」（只写这门技术本身常见的产物类型：控制台程序 / 页面与组件 / 表格与数据处理）。条数与顺序都不许变；用户**已经写了一整句**时就只润色那一句、不再往上堆。

**其余字段一律不放松**：经历与项目（STAR 四段）、教育亮点、自我评价仍然只能改写、不能加事实（真机验证时"担任体育课代表"原样保留）。

**机械闸跟着改了口径**（`resume_service.py`）：`_lists_are_lexically_equivalent`（技能条目必须与原文**逐字等价**）→ `_skill_items_kept`（**条数一一对应 + 每条必须仍然包含用户写的那项技术**，归一化后子串匹配）。旧的逐字等价会把"Java -> 熟悉 Java 基础语法…"这种正常润色判成违规并退回原文 —— 那正是用户看到的"没润色"。

**⚠️ 明确披露的机械缺口**（沿用 9.11 的披露体例，别当成做到了）：模型在条目里**额外**塞进用户没写过的技术名（`["Java"]` -> `["熟悉 Java 与 Python"]`）**机械上拦不住**。判"一串英文是不是技术名"需要一份技术名词表，而"IO 流""面向对象"这类**正当**的展开词与"Python"这类**越界**词在字符串层面无法区分。这一层由 prompt 的四不许 + 人眼兜底（用户原文留在 `parsed_data["_original"]` 里，可逐字段对照"AI 是不是偷偷加了东西"）。

**前端配套改动（两处，缺一不可）**：

1. **技能改成"一项一行"**：模板给技能字段下发 `lines: true`，前端渲染成**多行输入框**、只按**换行**切分（`splitLines`）。不能再用原来那个顿号分隔的单行输入框 —— 展开后的一句话自带顿号逗号（"熟悉 Java 基础语法、面向对象编程、集合框架…"），按顿号切会把一句话切成好几项假技能。
2. **展示态分两种排法**（`ResumePreview`）：全是短词条（≤12 字且无句读）时仍用「、」拼一行；只要有一条是展开后的句子，就**一条一行**排（否则顿号拼出来连成一坨、读不出边界）。

**顺手修掉的一个文案 bug**：润色失败时界面印成「润色这次没成功：**润色这次没成功**，你写的内容还都在这一页上…」—— `polishErrorText()` 的兜底句自己带着"润色这次没成功"，而卡片标题又加了同样的前缀。现在它只返回**原因**（拿不到后端消息时说明"多半是网络或 AI 服务临时不稳，也可能是后端刚重启过"）。

### 9.21 面试复盘**从来没成功过**：一个签名漏参 + 两个前端缺口 [已决策]

**用户原话**：「**面试复盘完全没有功能，依旧简单复盘即可，提出建议即可**」，并附截图：复盘页提示「内容不存在」+「这份复盘还没生成」。

**查出来的根因（三个都是真 bug，不是"没做"）**：

1. **`chat_prompt_json()` 的签名漏了 `max_tokens`** —— `interview_service._build_review()` 传了 `max_tokens=3000`，直接 `TypeError` → `POST /interview/{id}/finish` **永远 HTTP 500，而且 0.0 秒就崩**。后果：**面试复盘自上线以来一次都没生成过**（库里两场面试全卡在 `status='进行中'`、`report` 全是 `null`）。
   - 修法：给 `chat_prompt_json()` 补上 `max_tokens: int = 2048` 并**透传给 `chat_json()`** —— 保住调用方想要的 3000（复盘是"逐题点评 + 5 维评分 + 标签"的长 JSON，2048 容易截断），而不是把参数删掉。
   - 这个 bug 的形态值得记一笔：**它不是 AI 出错，是代码压根没跑起来**，所以任何"AI 兜底"都救不了它 —— 只有真跑一遍全链路才会暴露。
2. **前端「结束面试」按钮只 `navigate('/interview')`，从不调 finish** —— 用户提前结束（或答完最后一题之外的所有路径）就永远没有复盘。修法：按钮**真的调 finish**（并给出「正在生成复盘…」状态、期间禁用其它按钮），然后进复盘页。
3. **前端 axios 默认超时只有 20 秒**，而复盘要生成的 JSON 实测 7.9 秒、网络或模型慢时必然超时 → 请求被掐断，用户看到"生成复盘失败"而后端其实还在跑。修法：`interviewApi.finish` 单独给 **120 秒超时**（与简历润色同一做法）。

**两处配套（不然用户还是走不出来）**：

4. **复盘页那个「重新加载」是死按钮**：报告不存在时 `GET /review` 永远返回 2001，点多少次都没用。改成 **「生成复盘」**：就地调 `finish` 补一份再读 —— 用户不必回到面试页重新走一遍。这同时把用户当时**卡住的那场面试**救了回来。
5. **finish 不再可能 500**：`_build_review()` 外面包了一层兜底，AI 挂了（网络/解析/任何意外异常）就返回**规则版最小复盘** `_fallback_review()`：点出哪一题跳过了、哪一题答得太短、给一条通用建议；**不评分、不编优点**（`overall_score` 留 0、逐题点评**不带 score 字段**、库里多一个 `"fallback": true` 标记）。前端对"没有维度分数"的复盘**不再显示 `0 / 100`**（那是假分数），改说「本次没有 AI 评分」。

**验证（真机真 Key，探针账号用完即清）**：

- 全链路：`start` → 3 题作答（含追问，共 5 次 answer）→ `finish` **HTTP 200 / 7.9 秒 / status 已完成**；报告含 5 维评分（沟通表达 15 / 逻辑思维 10 / 专业基础 10 / 项目经验 10 / 求职动机 20）、3 条逐题点评（含 `better_answer`）、2 条优点、3 条改进、summary 与回流 tags；`GET /review` 200 读得回来。
- 兜底路径：monkeypatch 让 `chat_prompt_json` 抛异常 → `finish` 仍返回「已完成」+ `fallback: true`，出参 `InterviewReviewResponse` schema 校验通过，逐题点评都不带假分数。
- 前端 `npm run build` exit 0；**复盘/面试这几个文件**没有新增告警（`InterviewReviewPage.tsx` 唯一那条是 `load` 在 effect 里 setState，改动前就有；全仓口径见 9.20 的澄清，共 21 条）。
- 用户数据一行未动：`admin` / 「你大爷」两份简历、两场面试原样保留（他那场 `进行中` 的面试现在可以在复盘页一键补生成）。

#### 9.23.2 打包才会暴露的 5 个坑（全部已修，都记进 README 与代码注释）

1. **前端资源绝对路径** → `file://` 下白屏。修：`vite.config.ts` 加 `base: './'`。
2. **`createBrowserRouter` + `file://`** → 打开就是 404 页（pathname 是文件路径，路由匹配不上）。修：`router/index.tsx` **按 `window.location.protocol` 条件切换** `createHashRouter`。为什么不做成无条件 hash：Web 版与 `tools/render-check` 的 URL 断言都基于真实路径（`/chat` 等），无条件改会让回归全红。
3. **没有 vite 代理** → 接口全打到 `file://`。修：`frontend/.env.electron` 写绝对地址。
4. **`.env` 是 cwd 相对读的**（勘误 9.14）→ 后端起来但 AI 全哑。修：主进程 spawn 时 `cwd = resources\backend`；打包脚本把 `.env` 复制到 exe 同级，**全包只留一份**（含 Key，两份容易漏改）。
5. **SQLite 路径按代码位置解析**（`session.py` 的 `BACKEND_ROOT = Path(__file__).parents[2]`）→ 数据落到 `_internal\data\` 里，用户找不到、重打包就丢。修：`run_server.py` 在 **import app 之前**把 `DATABASE_URL` 钉到 `<exe 同级>/data/app.db`。

#### 9.23.3 PyInstaller / electron-builder 自己的坑

- **字符串动态导入看不见**：`uvicorn.run("app.main:app")` 会让 PyInstaller **漏掉 fastapi**（启动直接 `ModuleNotFoundError`）。修：入口写成 `from app.main import app` 再 `uvicorn.run(app, ...)`；`--add-data` 只带 `app/ai/prompts`（prompt 是 `.txt`，静态分析看不见），**不要**把整个 `app` 当数据塞进去（磁盘上多一份 `main.py` 会与冻结模块打架）。
- **`init_db()` 的 `create_tables` 默认是 `False`**（那是 CLI 的默认值）：打包入口必须显式传 True，否则新机器上所有接口死在 `no such table: users`。
- **`electron-builder.yml` 的 `files` 漏了前端** → `loadFile` 抛未处理异常 → **主进程静默退出**（双击"闪一下没了"，无任何提示）。修：`files` 加 `../frontend/dist → frontend/dist`；并给 `whenReady().then()` 补了 `.catch()` 弹框 —— 未处理的 promise rejection 会直接结束 Electron 主进程，这个 catch 是排查这类问题的唯一线索。
- **`portable` 目标不能用**：它每次解压到临时目录，内置后端的数据库跟着临时目录走，表现为"每开一次数据都清空"。所以 `win.target` 只用 **`dir`**。
- `.ps1` 脚本必须存成 **UTF-8 with BOM**，否则 PowerShell 5.1 按 GBK 读，中文注释会把脚本语法弄坏（本项目既有的坑，这次新建的两个 `.ps1` 都带了 BOM）。
